Purpose

What this tool is for

Linux desktops rarely use a single store. Apps arrive through apt, snaps, Flatpaks, Homebrew bottles, pipx tools, Rust crates, AppImages and vendor .deb downloads each with its own search, install and upgrade story.

lpkg sits above those managers. You ask once; it searches enabled backends, picks the best source by your priority list, installs, tracks provenance in a local registry and helps you upgrade, pin, export, or clean up without juggling five CLIs.

It does not replace apt or Flatpak it orchestrates them so day-to-day package work feels consistent on Ubuntu and Debian-based systems.

Get started

Install lpkg

Pick one path. After install, confirm with lpkg --version.

One-liner

Downloads the latest GitHub release binary, or builds from source if a release asset is unavailable.

curl -fsSL https://raw.githubusercontent.com/MatoloJr/lpkg/main/scripts/install.sh | bash

Clone and make

Default prefix is /usr/local. Override with PREFIX, BINDIR, or DATADIR.

git clone https://github.com/MatoloJr/lpkg.git
cd lpkg
sudo make install

Debian package

make deb
sudo dpkg -i dist/lpkg_0.2.0_amd64.deb

Cargo

cargo install --git https://github.com/MatoloJr/lpkg.git

Configuration

How to customize lpkg

Behavior is driven by a user config file, optional alias maps, install layout and JSON manifests so you can tune backends without rebuilding.

Main config ~/.config/lpkg/config.toml

Created on first run with sensible defaults. Edit it to change resolution order and which backends are active.

backend_priority = ["flatpak", "apt", "snap", "brew", "pipx", "cargo", "direct_deb", "appimage"]
apps_only = true
cache_ttl_hours = 24

[backends]
apt = true
snap = true
flatpak = true
brew = true
pipx = true
cargo = true
appimage = true
direct_deb = true

# Optional AppImage discovery roots
# appimage_paths = ["~/Applications", "~/.local/bin"]
  • backend_priority order used when lpkg install has no --source. First match wins.
  • [backends] set a backend to false to skip it in search/install/upgrade.
  • apps_only prefer application-like packages when listing (backends that support the distinction).
  • appimage_paths directories scanned for portable AppImages.
  • cache_ttl_hours how long inventory scan cache is considered fresh.

Aliases cross-backend identity

Packaged aliases live under /usr/local/share/lpkg/aliases.toml (or /usr/share/lpkg/). Drop a personal file at ~/.config/lpkg/aliases.toml to override and map one canonical name (e.g. firefox) to backend-specific IDs.

Install layout

When installing from source:

sudo make install PREFIX=/usr/local
# binary → $PREFIX/bin/lpkg
# data   → $PREFIX/share/lpkg/

Manifests reproducible machine setup

Export your inventory, edit the JSON, then reinstall elsewhere with import or install --all.

lpkg export -o packages.json
lpkg import packages.json --dry-run
lpkg install --all
lpkg install --all my-packages.json

Install provenance is tracked in ~/.local/share/lpkg/registry.db (SQLite). That registry is separate from backend package databases and survives tool reinstalls until you delete it.

lpkg search <query…>

Use case: discover where a package exists before you install.

Queries all enabled backends for each term you pass, then merges and dedupes candidates (same backend + id appears once). Pass multiple terms in one call when you are shopping for several apps. Empty search is rejected, listing every package on apt/Flathub is not useful.

  • --source apt,flatpak - limit search to listed backends (comma-separated).
lpkg search firefox
lpkg search firefox code
lpkg search neovim --source apt,brew

lpkg install [ids…] [options]

Use case: put software on the machine with one consistent interface.

Installs each package id in order. Without --source, the resolver walks backend_priority and picks the first enabled backend that can provide the package. Records the install in the local registry afterward.

  • --source <backend> - force a backend (e.g. flatpak, apt).
  • --version <ver> - pin a version when installing a single id (error if used with multiple ids).
  • --all [file] - bulk-install from a JSON manifest (default file: packages.json in the current directory).
  • -a / --auto - if the package is already installed, uninstall the old copy first, then install (replace / reinstall).
lpkg install firefox
lpkg install firefox code
lpkg install code --source apt
lpkg install firefox --auto
lpkg install --all
lpkg install --all my-packages.json

lpkg list [options]

Use case: see what is installed, what is stale and where you have duplicate copies.

Prints inventory across enabled backends (apps-focused by default). Use the flags below for audits, scripting, or cleanup decisions before uninstall / upgrade.

  • --outdated - only packages with a known newer version.
  • --duplicates - same canonical app installed via more than one backend.
  • --all - include non-app packages where backends support that distinction.
  • --format table|json - human table (default) or machine-readable JSON.
  • --source … - optional backend filter (comma-separated).
lpkg list
lpkg list --outdated
lpkg list --duplicates
lpkg list --all
lpkg list --format json

lpkg upgrade [id] [options]

Use case: keep packages current without manually invoking each package manager.

Behavior depends on flags. Bare upgrade (or upgrade --auto with no id) upgrades only packages reported as outdated. --all runs each backend’s native full upgrade. Targeting one id upgrades that install; with --auto, it upgrades only if outdated and exits quietly if already current.

  • --all - backend upgrade_all for every enabled manager (broader than outdated-only).
  • -a / --auto - outdated-only mode when no id; with an id, skip if up to date.
  • --dry-run - print what would be upgraded without applying changes.
  • --source <backend> - restrict to one backend.
lpkg upgrade
lpkg upgrade --auto
lpkg upgrade --all
lpkg upgrade firefox
lpkg upgrade firefox --auto
lpkg upgrade --dry-run

lpkg uninstall <id> [options]

Use case: remove an application or tool you no longer want, through the right backend.

Finds installed copies matching the id, asks that backend to uninstall and removes the registry entry. This is for packages managed via lpkg - not for removing the lpkg binary itself (see Uninstall).

  • --purge - remove config/data where the backend supports purge (notably apt).
  • --source <backend> - if duplicates exist, remove only the copy from that backend.
lpkg uninstall firefox
lpkg uninstall firefox --purge
lpkg uninstall code --source apt

lpkg cleanup [--source …]

Use case: reclaim disk after upgrades - old snap revisions, unused Flatpak runtimes, caches, etc.

Runs each enabled backend’s cleanup routine and prints a short freed/status report per backend. Safe maintenance after large upgrade sessions.

  • --source snap,flatpak - clean only listed backends.
lpkg cleanup
lpkg cleanup --source snap

lpkg info <id>

Use case: inspect before you reinstall, switch backends, or use --auto.

Shows currently installed copies (backend, version, outdated hints) and live search candidates for the same id. Prefer this when you are unsure whether something is apt vs Flatpak, or whether an update is available. 

lpkg info firefox

lpkg which <id>

Use case: answer “which package manager owns this install?” in one line.

Prints backend, backend-specific id and version for each installed match. Errors if the package is not installed. Handy in scripts or when resolving duplicate installs. 

lpkg which firefox

lpkg scan

Use case: refresh lpkg’s inventory cache after installing outside of lpkg or changing backends.

Lists installed packages from enabled backends, writes a scan cache into the registry and prints per-backend counts. Run this when list feels stale relative to the system. 

lpkg scan

lpkg doctor

Use case: diagnose why search/install fails or the system looks unhealthy.

Checks which backends are available vs enabled, warns about dpkg locks, reports duplicate installations, and summarizes registry tracking. Exits non-zero when issues are found - useful in CI or post-install checks. 

lpkg doctor

lpkg pin add|remove|list

Use case: freeze a package so routine upgrades leave it alone (distro version, known-good build).

Pins are recorded in the registry and applied via the owning backend when supported. Always pin an installed package; use --source when multiple backends provide it.

  • pin add <id> [--source …] [--reason "…"] - prevent upgrades; reason is for your notes.
  • pin remove <id> [--source …] - allow upgrades again.
  • pin list - show pinned packages and reasons.
lpkg pin add firefox --reason "distro version"
lpkg pin list
lpkg pin remove firefox

lpkg export -o <file>

Use case: snapshot your package set for backup or another machine.

Writes a JSON manifest of installed packages (and pin metadata when present). Pair with import or install --all to recreate the environment. 

lpkg export -o packages.json

lpkg import <file> [--dry-run]

Use case: reinstall from a previously exported manifest.

Reads the JSON and installs each entry via the recorded backend; re-applies pins when the manifest includes them. Use --dry-run to preview without changing the system. 

lpkg import packages.json --dry-run
lpkg import packages.json

lpkg completions <shell>

Use case: tab-complete subcommands and flags in your shell.

Emits completion scripts for shells supported by clap (e.g. bash, zsh, fish, powershell, elvish). Redirect the output into your shell’s completion directory. 

lpkg completions bash | sudo tee /etc/bash_completion.d/lpkg
lpkg completions zsh > ~/.zfunc/_lpkg

lpkg --version

Use case: confirm which lpkg build is on your PATH.

Prints the crate version (currently 0.2.0). Also available as -V. Use after install, upgrade of the tool, or when reporting bugs. 

lpkg --version
lpkg -V

Removal

Uninstall packages vs uninstall lpkg

These are different operations. One removes software you manage with lpkg; the other removes the lpkg binary itself.

Managed packages

Remove an app or package

Use the CLI. This asks the underlying backend (apt, flatpak, …) to uninstall and updates lpkg’s registry. Optional --purge removes config where the backend supports it; --source picks which copy when duplicates exist. 

lpkg uninstall firefox
lpkg uninstall firefox --purge
lpkg uninstall code --source apt
The lpkg tool

Remove lpkg from your system

How you installed determines how you uninstall. make uninstall only deletes the binary and shared data under your install prefix it does not remove user config or the registry.

Installed with clone + make

From the repo directory (use the same PREFIX you used for install; default is /usr/local): 

sudo make uninstall
# removes: $PREFIX/bin/lpkg
#          $PREFIX/share/lpkg/

Custom prefix example:

sudo make uninstall PREFIX=/usr/local

Installed from a .deb

sudo dpkg -r lpkg
# or
sudo apt remove lpkg

Installed with cargo

cargo uninstall lpkg

Installed via one-liner / manual binary

sudo rm -f /usr/local/bin/lpkg
sudo rm -rf /usr/local/share/lpkg

User data is kept on purpose. After removing the tool, you may still have ~/.config/lpkg/ (config, aliases) and ~/.local/share/lpkg/ (registry). To wipe those as well: 

rm -rf ~/.config/lpkg ~/.local/share/lpkg
